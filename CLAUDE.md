# Builder Listing System

Private back-office system for new-construction home builders in Texas. This file is the source of truth for project rules; `docs/` holds the detailed plans. If anything elsewhere disagrees, this repository wins.

## What this is

- A private system where listing data, photos and videos are created, organized and approved.
- Only our staff and our builder clients log in. Nothing is visible to anyone signed out.
- **Never public-facing.** No consumer website, no public listing pages, no home-buyer accounts, no SEO or public search. The MLS is the public outlet.
  - **One approved exception (owners, 27 Oct 2026): realtor share links.** Each home has one standing, unlisted link anyone at the builder who can see the home (salespeople included) can copy and send, so a realtor can download its photos and videos and click through to the builder's website. These pages are never indexed, never listed anywhere, show only that one home, can be replaced or deleted at any time, and log every view and download. The standing link has no end date (owners' decision, 27 Oct 2026); older one-off links made for a named realtor still expire.
  - **Second approved exception (owners, 28 Oct 2026): the join page** (`/join/[token]`), where someone with a join link our admins made sets up their own login. It shows only the role and builder the link is for, and nothing else.
  - **Third (owners, 28 Oct 2026): the invite page** (`/accept/[token]`), where someone we or their company invited continues to choosing a password. It shows only their first name and company.
  - **Fourth (owners, 30 Oct 2026): one-off broker links** (`/w/[token]`). A builder in broker mode can send one open work order to a broker who has no account. The page shows only that work order's sheet (what a signed-in broker sees for it), works until the work order is accepted or the link is turned off, is never indexed, and every open is logged. Nothing else may be public.

## The MLS

- Our team enters approved listings into the MLS **by hand**. The MLS does not accept data from us. Never build anything that sends data to the MLS.
- The MLS can send data **to** us through a read-only feed (usually the RESO Web API). We use it for MLS numbers, status tracking and the comparison checker.
- Store listing fields in RESO standard names and formats so MLS data lines up with ours.

## Non-negotiable rules

1. **Each builder company is a separate tenant.** Builder A can never see Builder B's data, photos or videos.
2. **Permissions are enforced in the database** with Supabase row-level security (RLS), not just by hiding things on screen. Every new table gets RLS policies in the same change that creates it. Every new `public` trigger function gets `revoke execute ... from public, anon, authenticated` in the same change (triggers still fire); every new callable `security definer` function checks the caller itself and revokes `anon` unless it's a share-link function. Yes/no permission helpers (`private.can_*`) always return true or false, never null (wrap them in `coalesce(..., false)`): people with no builder (photographers) or who were just turned off would otherwise slip past a check written as `if not private.can_...`.
3. **Every field records its source:** website, staff, or MLS.
4. **Imports never silently overwrite staff edits.** New or changed data from builder websites goes to a review queue.
5. **Media is private.** Files are locked by default and viewed only through links that expire. Uploads go straight from the browser to storage, not through our server. Target home is Cloudflare (R2 for photos, Stream for video); for the test phase, uploads use a private Supabase Storage bucket (`media`). Storage calls live in `src/app/api/media/[id]/route.ts` and `src/app/(app)/media/upload/`, so moving to Cloudflare before launch is contained.
6. **Deletes go to a 30-day trash first**, and every change is written to the activity log.
7. **No real builder data** goes into the system until backups and a security review are done. Until then, use realistic fake data only.
8. **One template for every builder.** All builders share one codebase, one database and one deployment. Never copy the code or make a separate deployment for a builder, and never write code that checks which builder it is (no builder names, IDs or slugs in code or migrations; demo builders belong only in `supabase/seed/`). When one builder needs something different, make it a setting or feature switch any builder could use (see "Builder settings and feature switches"), with a default that keeps every other builder as it is.

## Tech stack

- Next.js (app framework), hosted on Vercel
- Supabase: database, logins, RLS. Separate test and live projects.
- Cloudflare R2 (photos) and Cloudflare Stream (video)
- Sentry for error alerts
- Claude API: photo labeling (Haiku 5.5), floor plan and brand guide reading (Sonnet 5.5), paid from per-builder AI credits
- Later: Resend (email), Stripe (billing), HubSpot sync

- The owners understand tech but are not developers. Explain changes in plain language and recommend one option rather than listing many.
- Build one feature at a time and test it before starting the next.
- Builder website imports all go through one shared import door; each source is a small connector.

## How the code is laid out

- `supabase/migrations/` — every database change, in order. The database's security rules live here. Never change the database by hand without adding a migration file. Each file's leading number is unique and the files sort in the order they were applied; a new enum value is added in an earlier file than the one that first uses it (Postgres won't use a new value in the same transaction).
- `scripts/db-replay/` — the practice run: builds a brand-new Postgres 17 from `supabase/migrations/` and loads the demo seed (`cd scripts/db-replay && npm install && node replay.mjs ../..`, as a normal user, not root). It runs on GitHub for every change to `supabase/` (`.github/workflows/db-replay.yml`); a failure there means the live project couldn't be built from the repo.
- `src/lib/safe-path.ts` — `safePath()`: the only check for "send them back to this page" addresses (form `back` fields, `next=`, notification links). It refuses anything that could lead off the site, including `/\evil.com`.
- `supabase/seed/demo_data.sql` — fake builders, homes and `@demo.test` logins for the TEST project only. The demo password is not in the repo. Then, in order: `demo_media.sql`, `demo_photo_requests.sql`, `demo_round3.sql`, `demo_mls.sql`, `demo_plans.sql`, `demo_incentives.sql`, `demo_tasks.sql`, `demo_billing.sql`, `demo_more_builders.sql`, `demo_broker.sql`. There is one demo builder per billing plan: Mesquite Creek (Listing Service+ and Photos), Prairie Lantern (Software and Photos; broker mode, listing through Blake Sutton, `broker@demo.test`), Cedar Hollow (Software only, enters its own MLS) and Redbud Ridge (Listing Service+ only), each fully onboarded with made-up details; new demo logins copy the existing demo password's hash, so the seed never needs the password. Demo logos are drawn by `src/lib/demo-logo.ts` from a `<builder>/demo-logo/<color>/<Name>.svg` logo path instead of a stored file.
- `src/proxy.ts` — sends anyone signed out to `/login`.
- `src/lib/permissions.ts` — what each role sees on screen. Mirrors the database rules; the database is the real enforcement.
- `src/app/(app)/` — the signed-in screens: communities (start page, add a community) and each community's homes, all homes, home detail (edit, approvals, listing status, open houses incl. repeating, reverse prospecting, photo requests, change requests), add a home, approvals, media library, photo requests, photographer jobs and earnings, tasks (our team), team (builder owners/managers), website check, help, setup checklist (`/setup`), community setup (`communities/[id]/setup`), admin.
- `src/lib/menu.ts` — which tabs show on top for each role (Communities, Homes, Floor plans, Media in the middle) and the builder's feature switches (owners, managers and marketing get Tasks, their builder board; builders who enter their own MLS also get MLS work); everything else is in the menu. Request comps is a tile in each home's row of quick links and a button on each community, plus Comps in the menu.
- `src/components/home-art.tsx`, `src/components/media-art.tsx` — drawn pictures (exteriors, rooms, floor plans, community scenes) for demo media. `demo-media/videos/` holds four short demo videos.
- `src/app/(app)/media/` — media library (builder > community > home folders, room/type/tag filters, search), item page (download, tags, cover, trash), upload.
- `src/app/api/media/[id]/route.ts` — the only way files are served: reads the media record as the signed-in user (RLS decides), then redirects to an hour-long storage link or streams a demo video.
- `src/app/(app)/admin/` — platform admins only: overview, onboarding (add a builder, invite the owner, agreement and billing details), builders, communities (assign to a builder), people (roles, sales community assignments, invites), change-request inbox.
- Next.js 16: middleware is called `proxy`, and Cache Components is on, so pages that read the signed-in user wrap that part in `<Suspense>`. Read `node_modules/next/dist/docs/` before using unfamiliar Next.js APIs.

## Design

**Click feedback (every screen, nothing to add per page):** `ClickFeedback` (`src/components/click-feedback.tsx`, in the root layout) listens in the capture phase on window, before Next.js links and server-action forms cancel the browser's default. Any link to another page or any form submit shows a thin bar sliding across the top of the window, and that's the only visible feedback (owners' choice, 28 Oct 2026: no spinning cursor, no dimmed buttons, no notes). Behind the scenes the clicked link or button ignores further clicks (`data-pending`) and a form can't be sent twice (`data-pending-form`). The bar clears once the new page has replaced its grey loading placeholders (`animate-pulse`; keep using that class for Suspense fallbacks), when the page's content changes, or after 15 seconds. `PendingButton` ("Saving…" text) still works on its own. Clickable things show the pointing hand (`globals.css`).

**Jumps and prices (owners, 29 Oct 2026):** a link or tile pointing at a section on the same page (`#id`, e.g. Reverse prospecting, Download media) glides there smoothly and opens it (`OpenSectionOnHash`; reduced-motion users get an instant jump). Every price box shows thousands commas while typing: give the input `{...MONEY_INPUT}` and a `withCommas()` starting value (`src/lib/money-input.ts`); one listener in the root layout (`MoneyCommas`) does the rest. Servers already strip `$` and `,`.

**Cards or list (owners, 29 Oct 2026):** Homes, Communities and each community's homes have a Cards / List toggle (`ViewToggle`, remembered per browser in the `homes_view` / `communities_view` cookies, read by `viewPref`). The list is a `FilterTable` (search, filters, sorting; `pageSize`, `minWidth` props) with the key facts; home rows come from `src/lib/home-list.ts` (`homeRow`, add `HOME_LIST_EXTRA` to the select). The list view skips loading cover photos.

**Lists on phones and "Needs you" (owners, 30 Oct 2026):** on phones a `FilterTable` whose rows carry a `summary` opens as stacked rows (title with its key number, one grey line, small status chips), homes and communities that need the person first, with a Filter button for the dropdowns and a sort picker. A **Summary / All details** switch shows the full table instead, scrolling sideways with the first column pinned; each phone remembers the choice per list (localStorage `list_mode_<noun>`). Computers always get the full table. "Needs you" is worked out per person by `loadNeedsYou` (`src/lib/needs-you.ts`): owners, managers and marketing get homes waiting for their approval, open builder alerts, and approved homes to enter when they enter their own MLS listings; sales get open alerts on their communities; our staff ("Needs our team") get approved homes our team enters and team alerts. It's the first number column on computers (Communities list, Homes list, each community's homes). Give any new list a `summary` so it works the same on phones. **Every home row on a phone always shows its MLS status chip first** (Draft, In review, Ready for MLS, Live · N days, Under contract, Sold; owners: "the point of this software"), then the "needs you" chip if there is one; never drop it to save space.

**Page speed rules (keep these on new code; owners' request, 28 Oct 2026):** `requireProfile()` is cached once per page load (React `cache`) and checks the sign-in with `supabase.auth.getClaims()`, not `getUser()`; call it as often as you like. `src/proxy.ts` uses `getClaims()` too (its `user_metadata.needs_password` comes from the login token, so `setFirstPassword` refreshes the session after changing it). Run independent lookups together with `Promise.all`, never one `await` after another (the header in `src/app/(app)/layout.tsx` does this). Server code runs in Vercel's Cleveland region (`vercel.json`, `cle1`) next to Supabase (us-east-2). Permission rules write `(select auth.uid())`, not bare `auth.uid()`, so Postgres works it out once per query; columns that pages filter by get an index (migration `20261028000056_speed_rls_and_indexes`).

Choosing communities for a person (Team, Admin > People, join links) uses `CommunityPicker` (`src/components/community-picker.tsx`): the chosen ones as tags with ×, a search box with a short dropdown to add more, and Add all / Clear, so a builder with 50 communities doesn't get 50 checkboxes. On Team and Admin > People each salesperson's picker is folded to one line ("Communities: Oak Creek, Willow Bend Ranch +3 · Change", `CommunitiesFold`). Use it for any new "which communities" choice.

Lists of builders (Admin > Builders, Admin > Onboarding) fold to one line per builder (`<details data-builder-fold data-name>`), with a name filter, Open all / Close all, and `#<id>` links opening that builder (`BuilderListTools`, `src/components/builder-list-tools.tsx`). Keep any new per-builder admin list the same way, since there may be 50+ builders.


**Back buttons go back to where the person came from** (owners, 28 Oct 2026). `NavTrail` (`src/components/nav-trail.tsx`, in the root layout) keeps this tab's trail of pages in sessionStorage (`src/lib/nav-trail.ts`): saves on the same page (?saved=…) don't add a step, one-time notices (`saved`, `error`, `at`, `undo`, `link`) are dropped, going back takes the step off, and leaving by a link remembers the section it was in (`details[id]` / `section[id]`). `BackButton` (`src/components/back-button.tsx`) goes to the previous page and section, labelled "Back to {that page's heading}"; its `href` and `label` are only the fallback when there's no earlier page (a bookmark, an email link, a new tab). A page can name itself for these labels with `data-back-name` (a home's media folder is "Photos of {address}", so it's never mistaken for the home). Top-level pages with no natural parent use `onlyWithTrail` (shown only when there's an earlier page): the media library has one above its folder path. Every "←" back link uses `BackButton` (`variant="text"` for the small grey ones); don't add fixed-parent back links. Step-by-step Back/Next (setup checklist, Add a home) stays as it is.

**Home page sections fold** (owners, 28 Oct 2026): every section on a home's page below the top tiles (incentives, open houses, reverse prospecting, listing photos, social media reel, share, photo requests, change requests, room sizes, each block of listing details, NTREIS details, activity) is a `HomeSection` (`src/components/home-section.tsx`): one line with the title, a short count and a hint, closed by default, opening after a save in it (`open={at === id}`). `OpenSectionOnHash` opens a section when a tile or link points at its `#id`, and keeps people in place across saves: any form submit remembers the open sections (`details[id]`, so give every fold an `id`) and the scroll spot in sessionStorage, and when the page comes back from the save they're reopened and scrolled back (it wins over the redirect's `#section`). Price has a history with undo: every change from the activity log, newest first, with "Undo: go back to $…" on the current one (a plain `saveHome` with the old price, `at=price`). They're ordered by how often people use them, under four small group labels: **Day to day** (open houses, incentives, price, change requests), **Ask our team** (reverse prospecting, photo requests), **Photos and marketing** (listing photos and tours, social media reel, share with a realtor), **Listing details** (description, specs, construction, location, NTREIS details, room sizes, activity). Price has its own small section (a separate `saveHome` form with only `list_price`), not in Specs. New sections on that page use `HomeSection` too and go in the group that matches how often they're used.

White canvas, Figtree type, "bluebonnet" blue (#3452c7) as the single accent. Image-first cards like the big listing sites. Keep new screens consistent with `src/components/home-card.tsx` and the home detail page.

## Media

**Photo speed rules (keep these on every new screen):** grids, cards and folder covers use `MediaPicture` (default `size="thumb"`), never the original file; a photo's own page uses `size="web"`; only downloads and the MLS photo pack fetch the original. Pictures load lazily as they scroll into view. Lists that can grow (media results, folders) are paged, and counts come from the database (`community_media_counts`, `home_media_counts`), never by loading every row. Uploads make the preview copies in the browser (`src/lib/previews.ts`): `thumb_path` (~640 px WebP, or a video's still frame) and `web_path` (~1600 px WebP), saved next to the original with `.thumb.webp` / `.web.webp`; if the browser can't read a file the original is used. `/api/media/[id]?size=thumb|web` serves them, falling back to the original, with a day-long private storage link the browser may reuse for 23 hours (owners asked for speed, 28 Oct 2026), so repeat visits load cards from the browser's own cache; originals and downloads keep hour-long links. The first few pictures on a page (`MediaPicture priority`: the first 3–4 cards, a home's main photo, a community banner) load right away at high priority, the rest lazily as they scroll in, and the root layout opens the connection to storage early (`preconnect`). Community cards show one picture (the community's cover, else one of its homes'). AI labeling reads `web_path` when there is one. Realtor share pages use the same copies through `/s/[token]/file/[id]?size=…` (`share_file` returns the preview paths; `share_access.file_is_shared` accepts them).

`media` rows belong to a builder, optionally a community, optionally a home (a home's builder and community are filled in automatically). Each has a room label and tags; the address, plan, community and room are added as tags automatically, and `search_text` powers search. Who sees media follows homes: staff all, builders their own, sales only their communities (plus builder-wide items). Owners, managers, marketing and our admins upload and edit. Nothing is hard-deleted; `deleted_at` is the trash.

**Media page views and the archive (owners, 29 Oct 2026).** The library leads with All / Photos / Videos / Floor plans / Community photos (`kind=community` = a community's own items); rooms, tags and Archived files are under "More filters". Files over `app_settings.media_archive_days` (600) old move to the archive nightly (pg_cron `media-archive`, `private.run_media_archive`, migration `20261029000073_media_archive`), but only when nothing still uses them: a home's files once it's sold or off the market (or deleted), a community's own files once every home in it is, never the floor plan library. Archived files (`media.archived_at`) are hidden from the library's normal views and folder counts, still downloadable, and come back with "Bring back from the archive" on the file's page (then `archive_hold_until` keeps the job off them for 180 days); owners, managers, marketing and our admins archive or bring back (`media_archive_guard`). Nothing is deleted; `media.storage_class` is for the move of archived originals to cheaper storage (Cloudflare R2 Infrequent Access) when media moves to Cloudflare. Admin's storage meter shows the archive (`public.media_archive_summary`).

**Our photographer's deliveries wait for approval (owners, 29 Oct 2026).** Files a photographer uploads start as `media.review_status = 'pending'` (`media_review_guard`): they show in the library with "Waiting for approval", but don't go on the home's listing, the realtor page (`private.shared_media_ids`) or cards (`home_cover_photos`) until approved; `listing_media_prepare` refuses them. When the shoot is marked delivered, marketing (or the owner and managers when the builder has no marketing people) gets an inbox notice and an email (`media_requests_review_notice`). They approve on the home ("Photos to approve" section, `PhotoApproval`, `src/components/photo-approval.tsx`; everything ticked, untick what not to use, or "Approve all") or on the community's media folder; "Looks good: approve the photos and mark complete" on the photo request does both. `public.review_media(ids, 'approved' | 'not_used')` runs as the person deciding (`private.can_review_media`: owner, managers, marketing, our admins); approving puts a home's files on its listing (and on the MLS update task for live listings). Everyone else's uploads stay `null` (approved) as before.

## Listing photos, video and tours (what goes on the MLS)

`listing_media` is each home's MLS list, in order: photos, floor plans, video and virtual tours. It fills itself: anything uploaded to the home (our photographer's deliveries or the builder's own uploads) except social media reels goes on the end (`media_to_listing`, `tours_to_listing`); trashing an item takes it off every listing. Community items (amenity, entrance, aerial, community video) and the floor plan library's photos are optional: the builder adds them on the home page (`listing_media_prepare` only accepts the home's own, its community's or its plan's items, same builder). Removing from the listing never deletes the file. `virtual_tours` holds tour links (Matterport, Zillow 3D Home, iGUIDE, Cupix, YouTube, Vimeo, other) for a home or a whole community, marked branded or unbranded, with who added them (`added_by_role`: photographer / builder / staff); photographers add them for their open jobs on the job upload page. Same RLS as media: owners, managers, marketing and our admins change listings; sales view. Screens: "Listing photos, video and tours" on each home (with "Download all N photos (.zip)" at a picked size and a link to every file; drag a photo onto another spot to reorder it (`ListingSortable`, `dropListingItem`; Earlier / Later stay for phones); click a photo's name to rename it in place (`RenameInline`, `renameListingPhoto`, the home's own photos only; it replaces the caption too, so AI never renames it back); "Let AI label them" for the home's photos with no room yet (`labelListingPhotos`, 1 credit each, shown only when AI is on); when every community or plan item is already on the listing, the optional lists say so instead of "none yet"; the "Download media" tile at the top of the home jumps here; `src/components/listing-media-panel.tsx`, actions in `homes/[id]/listing-actions.ts`), the last step of Add a home (our photographer → a photo request; our own → straight to upload; add the community's photos; tour links). Our team's MLS sheet and work sheets show MLS-ready photos in listing order, video downloads and tour links, with a "Download MLS photo pack" zip built in the browser (`photo-pack-button.tsx`, files 01-exterior.jpg, ... plus README with tour links; built client-side because Vercel caps server responses at ~4.5 MB). Readiness counts photos on the listing. On live listings, listing changes go on the MLS update task (`listing_media_changes`: photos added/removed, video, tours, photo order); the old `media_mls_changes` trigger is gone.

## Photo tags (one shared list)

Extra tags come only from `media_tags` (label, group: shot / inside / outside / community, other names, active). `media_prepare` maps whatever is sent to the list label (by name or other name, ignoring case) and drops anything not on the list; automatic tags (address, plan, community, room) are added as before, and a room that's also on the list uses the list's name. Retired tags can't be picked but stay on photos that have them. Admins manage the list at Admin > Photo tags: add, rename (`rename_media_tag`, every photo updates, old name kept as another name), merge (`merge_media_tags`) and retire. Anyone who tags photos (not sales) can ask for a new tag from a photo's page (`media_tag_requests`); admins add it, point to an existing tag (`approve_media_tag_request`) or decline. Screens use `TagPicker` (`src/components/tag-picker.tsx`): pick from the list, no free typing. The AI gets the list in its prompt and its tags are matched to it (`matchToList` in `src/lib/tags.ts`).

## AI photo labeling

After an upload, `src/lib/ai-tagging.ts` sends each JPG/PNG/WebP photo (by a 10-minute private link) to Claude Haiku 5.5 (`claude-haiku-5-5`), which suggests the room, up to 6 tags, a short caption and MLS warnings (blurry, dark, people, signs/logos, text). It runs after the response via `after()`, with the uploader's own database access. AI fills only what a person hasn't set; `room_source` / `caption_source` say `ai` or `staff`, and a person's edit flips them to `staff` (trigger `media_track_sources`). Photos start as MLS-ready (`media.mls_ready`, set on upload); only an AI warning or a person unticking it makes one "not ready" (migration `20261028000058_photos_ready_unless_flagged`), so a missing AI key or no credits never holds a listing up. Those show a small "● Check" on the photo with the reason on hover, and one line above the listing photos saying how many need a look. HEIC photos skip AI. Each photo uses 1 AI credit (see "AI credits"); when the builder is out, the photo is saved with `ai_status = 'no_credits'` and AI skips the rest of that batch. Needs `ANTHROPIC_API_KEY` in Vercel.

## AI credits

Every AI call is paid for from the builder's monthly AI credits (migration `20261028000045_ai_credits`, `src/lib/ai-credits.ts`). Costs are in `app_settings.ai_credit_costs`: photo label 1 credit (Haiku 5.5, about $0.0003 to us), floor plan read 25 and brand guide read 25 (Sonnet 5.5, about $0.02-0.04). Each builder gets `app_settings.ai_credits_default` (2,500) a month unless `ai_allowances` gives them their own (0 turns AI off for them); `ai_credit_grants` adds extra for one month. Months run on Central time and reset on the 1st. Code calls `spendCredits` (`public.ai_spend`, which reserves the credits or returns null when there aren't enough, one spender per builder at a time) before the AI call, and `finishCredits` (`public.ai_finish`) after it with the real tokens, or to give the credits back when the call failed. Runs by our staff and photographers are logged with `counts = false` and never use a builder's credits. `ai_usage` keeps every call with tokens and dollar cost (from `app_settings.ai_prices`; update it if Anthropic's prices change); only those two functions write it; staff see all, builder owners and managers their own. Screens: `AiCreditMeter` (`src/components/ai-credit-meter.tsx`) on Floor plans, each plan's file section and the upload page for builder users; Admin overview "AI credits this month" (`public.ai_usage_summary`) shows credits used, photo and plan counts and real cost per builder, with per-builder monthly credits, extra credits for this month and the default.

## Admin, invites and join links

Adding people needs `SUPABASE_SERVICE_ROLE_KEY` set in Vercel (server only, never in code or the browser); without it the invite form and join links are off and everything else in Admin works. No email is needed for either way of adding people.

**Invite links (no email needed).** Adding a person (Admin > Onboarding's owner, Admin > People, a builder's Team page) makes their login with `auth.admin.createUser` (`email_confirm: true`, no email sent; `src/lib/invite-links.ts`), marked `user_metadata.needs_password`. Whoever added them clicks "Get invite link" next to their name (`InviteLink`, `src/components/invite-link.tsx`, action `getInviteLink` in `src/app/(app)/invite-actions.ts`) and sends the link any way they like. The link is our own `/accept/<token>` (`invite_tokens`, migration `20261028000054_invite_link_tokens`; only our server writes it, platform admins can read it), good for 48 hours (`INVITE_HOURS`). Opening the page changes nothing: it shows the person's first name and company and a **Continue** button, and only that button signs them in (`acceptInvite`: a fresh Supabase magic-link token made and verified on the spot). This is on purpose: email security scanners (Outlook / Microsoft Safe Links) open every link in an email, and they used up Supabase's one-time links before people could click (seen 28 Oct 2026). After Continue they go to `/welcome` to confirm their name and choose a password (10+ characters), then straight to their setup checklist (or the start page); until then `src/proxy.ts` sends every page to `/welcome`, and the link keeps working. Setting the password marks their links used (`finishInvites`); "Make a new link" turns the old one off, and works only for people who haven't set a password yet, so a link can never be used to get into an active account. Who can make one: our admins for anyone; owners, managers and marketing for the people they can manage. `/accept/[token]` is signed-out (allowed in `src/proxy.ts`, `noindex`) and shows only the first name and company.

**Join links (one link, many people; self-onboarding).** Admin > People > Join links. A platform admin makes a link for one role (never platform admin), plus the builder for builder roles, the communities for sales, or the builders a coordinator works on; optional name, 7–90 days, optional most people. `join_links` (admins only; `join_links_prepare` keeps the token, role, builder and counts out of people's hands; turn off/on with `revoked_at`). The person opens `/join/[token]` (signed out, allowed in `src/proxy.ts`; reads only `public.join_link_info`), enters name, email, optional phone and a password; `joinWithLink` creates the login with the admin key (`email_confirm: true`, no email sent), then `public.redeem_join_link` (callable only with the admin key) sets up the profile, sales communities and coordinator builders, counts the use, marks the access history entry "with a join link" and notifies whoever made the link; they're signed straight in (owners chose no approval step; switch people off on Admin > People). Invite links are for one known person; join links are for a role, to send to several people who fill in their own details.

Standard prices are `app_settings.billing_defaults`; a builder's own prices (deals) override them column by column (null = standard). Nothing is charged before `builder_billing.starts_on`, or while plan is null.

Every billable event is a row in `billing_charges` with its price locked in. `invoice_month` says which invoice it can first go on: usage goes on the next month's invoice. On the 1st at 6 am Central (pg_cron `monthly-invoices`, `private.run_monthly_invoices`) a draft per builder (`invoices`) collects that month's software fee, the onboarding fee if unbilled, and every waiting charge due by then; admins get an inbox notice. `public.build_invoices(month, builder?)` (admins) rebuilds drafts any time; sent invoices are never changed. People can only: add adjustments; void (with a reason) or restore charges not on a sent invoice; mark a draft sent (gets `INV-YYYYMM-NNNN`, issue and due dates from `net_days`, default 15), paid (with a note) or back to unpaid; void an invoice with a reason (its charges go back to waiting and land on the next invoice); edit an invoice's printed note and QuickBooks number. Nothing is deleted (`billing_charges_guard`, `invoices_guard`; trusted database code sets `app.billing_system`). Platform admins only; builder owners see their plan and prices without deal notes (`public.my_billing`), their sent and paid invoices and their non-voided charges. Managers, marketing, sales and coordinators see no billing.

Screens: Admin > Billing (`/admin/billing`: totals, builders with what's on the next invoice so far, invoices, "Build drafts now", standard prices), each builder's plan, prices, waiting charges, credits and history (`/admin/billing/builders/[id]`), each invoice (`/admin/billing/invoices/[id]`: printable, Mark sent / paid / void, rebuild, notes), and the owner's Billing page (`/billing`, `/billing/invoices/[id]`). The invoice layout is `src/components/invoice-document.tsx`; print to PDF to send it. No money moves and nothing is emailed yet. Later: QuickBooks (customer and invoice IDs are already stored), Stripe or ACH payment, emailing invoices through Resend.

## Onboarding a builder

Three layers, each asking only for what the next step needs:

1. **Before the invite (our team, Admin > Onboarding, `/admin/onboarding`).** "Add a builder" lives here (Admin > Builders links to it): display name, legal company name (`builders.legal_name`, fills the MLS Owner Name; falls back to the display name), MLS markets, the primary contact's name and email (shown as "Primary contact" on these screens since 28 Oct 2026; they get the builder owner role, are our main point of contact until the builder names someone else, and their invite link is on the card), and our part of `builder_onboarding`: agreement and listing-authorization dates, what we charge, notes. Nothing else: the builder adds their own billing contact, website, title company and main contact on Company details, and listing feed questions (`website_platform`, `sends_listing_feed`, still in the table) wait for a later website-feed step (owners' decision, 28 Oct 2026). Each builder's card shows its stage, their checklist progress, what's "waiting on us", the owner's invite link, a read-only "From the builder" summary (main contact or owner, billing contact, website, title company), an owner form if there's no owner, and our details form. `builder_onboarding` is staff-read, admin-write (managers have no billing access); a row is made for every builder by `builders_add_onboarding`.
2. **The builder's setup checklist (`/setup`).** Owners, managers and marketing see it; a "Setup" top tab and a banner on the communities page show while it's open (`setupOpen`, `SetupBanner`), and "Setup checklist" stays in the menu. Setup counts as finished when they click "We're all set" or when every step is done (finished automatically on `/setup` or a step page), and the tab then leaves the top bar. Each page a step sends them to has a Back / Next bar along the bottom while setup is open (`SetupNav`, `src/components/setup-nav.tsx`, given the steps that page covers), with "Skip this for later" on skippable steps. "Who photographers call" is filled in right on the checklist (`PhotoContactForm`, also on Photo requests). Our staff open any builder's with `/setup?builder=` ("Builder setup" in the menu). Steps are worked out from real data in `src/lib/onboarding.ts` (`loadOnboarding`), so they tick themselves off: team, logo, brand guide, website (required), billing contact (the owner adds it), default title company, who photographers call, communities, each community's setup, salespeople on communities, floor plans, first home (approving a first listing is no longer a step; owners' decision, 28 Oct 2026). The only stored choices are steps skipped (team, brand guide, title company; and "for later": communities, which covers the whole communities section, and floor plans; migration `20261028000055_setup_skip_for_later`) and "We're all set" (`builder_onboarding.skipped`, `finished_at`). Once setup is marked done it stays done: no reopen button and no "marked done" note, the Setup tab and banner never come back, and the checklist lives only in the menu (owners, 28 Oct 2026), read and changed only through `public.builder_setup_state`, `set_setup_skip` and `finish_setup` (staff, or that builder's owner, a manager or marketing). Stages for Admin: Getting ready → Invited → Setting up → First community ready → First listing approved → Live on the MLS.
3. **Community setup (`/communities/[id]/setup`).** The MLS questions shared by every home in a community (schools, HOA, MUD/PID, utilities, lockbox, showing setup, directions), for that community's MLS (`communitySections`), with a "ready for the MLS" meter (`communityCompleteness`) and builder-friendly help. Answers live in `communities.mls_fields` (sources in `field_sources`, set by `communities_mls_fields_sources`); owners, managers, marketing and our admins edit (the community rules), coordinators view. Adding a community sends them straight here. On the MLS sheet a community field uses our team's `mls_details` entry if there is one, else the builder's answer (`mergeCommunityDetails`); saving the sheet doesn't store a value that matches the builder's answer, so it keeps following the builder. A changed answer goes on the MLS update task of every live home in the community (`community.<Key>`, `communities_mls_fields_changes`) unless our team has its own entry for that field.

## Default title company

Most builders close through one title company. It's set once per builder in `builder_settings` (`title_company_name`, `_location`, `_phone`, plus `_contact` and `_email` for the escrow officer, which only our team and the builder see): by the builder, on `/company#title-company` (Company details, owners, managers, marketing and our admins; `TitleCompanyFields`, `saveTitleCompany` in `company/actions.ts`), and as an optional setup checklist step. It fills NTREIS's Title Company Preferred / Location / Phone (`TitleCompanyPreferred`, `TitleCompanyLocation`, `TitleCompanyPhone`, community fields in the Financial section) through `titleDefaults()`: our team's entry wins, then the community's own answer (community setup, for a community that uses a different one), then the builder default (`mergeCommunityDetails(answers, staff, defaults)`). Changing the default puts the change on the MLS update task of every live home that uses it (`builder_settings_title_changes`); community answers that change what a live home uses do the same (`communities_mls_fields_changes`).

## Backups and error alerts

Three backup layers, set up per `docs/backups.md`: Supabase point-in-time recovery (live project, paid), hourly encrypted copy of the database and photo originals to Backblaze B2 (`.github/workflows/backup-hourly.yml`, `scripts/backup/`), and readable copies in Google Sheets and Dropbox. A restore drill (`restore-drill.yml`) runs quarterly. Nothing runs on the schedule until the GitHub variable `BACKUPS_ENABLED` is `true`. Sentry (`@sentry/nextjs`, `sentry.*.config.ts`, `src/instrumentation*.ts`) reports errors once `NEXT_PUBLIC_SENTRY_DSN` is set; it never sends user info, cookies, headers, form contents or query strings.
